# Bergbot — Product Requirements Document (Phase 1)

**Version:** 1.0 · 8 September 2026
**Companion documents:** `bergbot_product_spec.md` (strategy & architecture, all phases), `BERGBOT_WORK_ORDER.md` (build plan for Claude Code)
**Scope of this PRD:** Phase 1 — full operational launch, Switzerland, hiking. Later phases are referenced only where they constrain Phase 1 design.

---

## 1. Summary

Bergbot is an open-source mountain-planning agent. A user tells it, in English, French, German or Italian, where they want to go, what they want to do, or sends a GPX. Bergbot checks official Swiss data and the live web, puts warnings first, recommends routes, returns a ≤12-line chat answer plus a self-contained mobile HTML report, and hands over a GPX for swisstopo. It runs locally on the user's machine and AI subscription. It is playful by default, strictly serious about safety, and has a robot mascot who dresses for the activity.

Phase 1 success = GitHub stars and waitlist signups, generated by people forwarding Bergbot's reports.

## 2. Users and jobs

| User | Job to be done | Entry surface |
|---|---|---|
| Casual hiker | "Find me something for tomorrow that fits my legs and the train" | Telegram, WhatsApp via own agent |
| Group / family organiser | "Something everyone can do, with lunch, reachable by transport" | Telegram |
| Dog owner / bivouac planner | "Where is this allowed and is there a fire ban" | Telegram |
| Visitor to Switzerland | "I don't know the regions or the T-scale, help me" | Telegram, Claude.ai |
| Experienced hiker / guide | "Pre-brief this GPX against every official source, fast" | Claude Code, CLI |
| Developer / agent user | "Install it, extend a canton, read the code" | Claude Code, GitHub |

## 3. Goals and non-goals

**Goals (Phase 1)**
- G1 First-message success: a new user gets a useful, correct, warnings-first answer to their first sentence in any of four languages.
- G2 Complete product: find, around, audit, check, export, suggestions, media lookup and free conversation all work at launch.
- G3 Shareable: message + HTML + GPX can be forwarded and used by someone who never installed Bergbot.
- G4 Trustworthy: every finding sourced, timestamped, classified; no "safe" vocabulary anywhere.
- G5 Growth loop: report footer and website convert to stars and waitlist.
- G6 Installable in one command (plugin) or one guided flow (Telegram), with visual guides in four languages.

**Non-goals (Phase 1)**
- No hosted report pages, no accounts, no server-side memory.
- No Bergbot-owned WhatsApp number (Phase 3).
- No winter activities, MTB, trail running data (Phase 5) — but mascot variants and activity enums exist.
- No personalization profile or weekend planner (Phase 4).
- No monetisation of any kind.
- No route synthesis off official/known networks.

## 4. Surfaces

| Surface | Phase 1 | How Bergbot runs |
|---|---|---|
| Claude Code | Yes | Plugin from repo marketplace; host agent is the LLM; `bergbot` CLI does deterministic work |
| Claude.ai | Yes (verify) | Same plugin via Customize → Plugins → Add marketplace; falls back to "coming soon" tab if unsupported |

## 5. Functional requirements

Priority: **P0** must ship · **P1** should ship · **P2** nice to have.

### 5.1 Conversation
- FR-C1 (P0) Detect intent from natural language in EN/FR/DE/IT: `find`, `around`, `audit`, `check`, `export`, `media`, `help`, `chat`, `emergency`. An attached GPX/KML/GeoJSON implies `audit`.
- FR-C2 (P0) Extract constraints: region/canton/place, date/time window, max ascent, max distance/duration, difficulty ceiling (T-grade or words like "easy"), transport requirement and max travel time from origin, hut/restaurant, water, dog, bivouac/camping, group (kids, seniors), start/end preferences.
- FR-C3 (P0) Reply in the language of the user's last message; report in the same language.
- FR-C4 (P0) Suggested prompts on first contact, greeting, vague message, or `help`; 4 suggestions, localised, seasonal (month-aware), region-aware when a region is known. Telegram renders as tappable keyboard; CLI/Claude Code as numbered list.
- FR-C5 (P0) Follow-up handling: modifications ("shorter", "Sunday", "with a hut", "from the other side") mutate constraints and rerun only affected checks; questions ("what is T3?", "water on the way?", "ok for an 8-year-old?") are answered from audit context, data and web.
- FR-C6 (P0) Slash commands `/find /around /audit /check /gpx /help` in Claude Code and CLI; optional, never required.
- FR-C7 (P0) Emergency intent ("someone fell", "injured", "lost") short-circuits to: call 1414 (Rega) or 112, share location, stay put guidance; nothing else in that reply.
- FR-C8 (P1) General mountain Q&A not tied to a route (equipment, grading systems, how to read a bulletin).

### 5.2 Register (personality)
- FR-R1 (P0) Two registers: `playful` and `serious`. The **renderer** selects the register by rule; the model writes within it.
- FR-R2 (P0) `serious` is forced when: any warning of severity critical or important exists; avalanche, closure, fire restriction, shooting activity or exposed-wind finding is present; the user asks a safety question; intent is `emergency`.
- FR-R3 (P0) In `serious`: no humour, no emoji except severity markers 🔴🟠🟡, no mascot, no media offer unless asked.
- FR-R4 (P0) In `playful`: warm, short, native-language humour from the locale pack, mascot allowed, media offer allowed.
- FR-R5 (P0) Forbidden vocabulary in all registers and locales: "safe", "sicher (as verdict)", "sans danger", "sicuro (as verdict)", "should be fine", "go for it" and locale equivalents — enforced by test.

### 5.3 Workflows
- FR-W1 (P0) **find**: constraints → candidate routes from official hiking network + OSM → filter by hard constraints → check conditions for the time window → rank → 2–3 candidates with 2 lines each → on selection, full audit.
- FR-W2 (P0) **around**: place input (address, village, municipality, stop, lift station, hut, summit, coordinates, GPX) → resolve → suitable routes nearby, ranked → same output as find.
- FR-W3 (P0) **audit**: route (GPX/KML/GeoJSON or selected candidate) → full check list (§5.4) → warnings → message + report + files.
- FR-W4 (P0) **check**: single-status questions (lift running, hut open, pass/road open, fire ban in canton) → verified/unverified answer with source and timestamp.
- FR-W5 (P0) **export**: GPX (default), KML, GeoJSON of the selected route; delivered as chat attachment or local file; followed by the swisstopo import line.
- FR-W6 (P0) **media**: when the route is "famous" (curated list match, or prominence heuristic: SwitzerlandMobility national/regional route, ≥N web results for exact name) offer "photos and stories"; on request return 3–5 dated links (official page, gallery, recent trip report, video) marked third-party, not part of the audit. Links only; no re-hosted images.
- FR-W7 (P1) **help**: what Bergbot can do, in the user's language, with suggestions.

### 5.4 Audit checklist (P0 unless marked)
Route geometry and identity · distance, ascent, descent, duration (DIN 33466 or SAC time formula, stated) · activity type · SAC T1–T6 when available, else "not graded" · terrain: altitude range, slope, aspect, exposed segments · closures and diversions intersecting the route · weather along route by hour (temp, precipitation, thunderstorm risk) · wind and gusts on exposed sections · MeteoSwiss natural-hazard warnings · forest-fire danger level and current restrictions · wildlife quiet zones and protected areas · shooting-range zones and firing schedule for the date · livestock guardian dog areas · public transport out and back (times, last return) · cableway/lift schedule and status (verified/unverified) · huts and restaurants with open/unverified flag · nearby webcams (P1) · camping/bivouac/fire/dog rules where verifiable (P1) · water, shelters, POIs (P1) · escape points (P1) · known / inferred / uncertain / not verified summary · sources, source timestamps, retrieval timestamps, confidence.
Snow/avalanche context: P0 as **presence** ("SLF bulletin exists for this region, danger level X; Bergbot does not interpret it for hiking") — full winter handling is Phase 5.

### 5.5 Chat message
- FR-M1 (P0) ≤12 lines, plain text with minimal markdown (works on any channel), fixed order: warnings → route line → weather line → transport line → why-this-one → attachment → closing question.
- FR-M2 (P0) Closing question offers exactly: GPX · another suggestion · (if famous) photos & stories.
- FR-M3 (P0) Message must be self-sufficient if the HTML never opens.

### 5.6 HTML report
- FR-H1 (P0) One self-contained `.html` file, no external requests, no fonts, no JS required; renders in iOS static preview.
- FR-H2 (P0) Inline SVG map: route line over embedded static tile raster (licence-cleared), hazard markers, start/end, escape points.
- FR-H3 (P0) Inline SVG elevation profile with exposed/hazard segments coloured.
- FR-H4 (P0) Section order: Before you go → Route → Conditions → Terrain → Logistics → Around → Photos & stories (if requested) → Evidence → Footer.
- FR-H5 (P0) Evidence classes A–E displayed per finding (see §7).
- FR-H6 (P0) Footer: mascot, "Made with Bergbot", ★ Star · Install · Join waitlist (UTM-tagged links, no tracking pixels).
- FR-H7 (P0) File size < 2 MB; target < 1 MB.
- FR-H8 (P1) Progressive enhancement: with JS, map pans/zooms; without, identical static content.
- FR-H9 (P0) Mascot variant chosen by activity; **never rendered in or adjacent to the warnings block**; omitted entirely when any critical warning exists in the header area (footer only).

### 5.7 Mascot (assets provided by founder)
- FR-B1 (P0) Asset set in `brand/mascot/`: `default`, `hike`, `alpine-hike`, `ski-tour`, `trail-run`, plus any further variants supplied (e.g. `snowshoe`, `mtb`, `climb`). Founder supplies PNG/SVG; pipeline produces optimised WebP ≤ 40 KB and data-URI snippets for the report.
- FR-B2 (P0) Mapping activity → variant with fallback to `default`; mapping lives in `brand/mascot/manifest.json`.
- FR-B3 (P0) Uses: Telegram bot avatar (`default`), report header (activity variant), report footer (`default`), website hero and install page, README, empty states, suggestion card. Never in warnings, never in `serious` register messages, never on the Safety page.
- FR-B4 (P0) Until assets arrive, a neutral placeholder square with the variant name is used; build must not depend on the artwork.
- FR-B5 (P1) Mascot name and per-language one-line voice guide, to be provided.

### 5.8 Install & distribution
- FR-I1 (P0) Repo is a Claude plugin marketplace: `.claude-plugin/marketplace.json` + plugin manifest; `/plugin marketplace add <org>/bergbot` → `/plugin install bergbot` works from a fresh Claude Code.
- FR-I2 (P0) `pipx install bergbot` (PyPI) installs the CLI; `bergbot connect telegram` guides token entry and starts the poller; `bergbot doctor` checks keys, data caches, tokens.
- FR-I3 (P0) Install guides with one screenshot per step and copy buttons, per surface, in four languages, on the website and in `docs/`.
- FR-I4 (P0) Website: static, four languages, pages Home · Install · Connect · Examples · Coverage · Safety & sources · Roadmap · Waitlist; hero uses mascot and a real Telegram screenshot + report.
- FR-I5 (P0) Waitlist form (email, language, region, activities, free-text wish, interest checkboxes) — third-party form or serverless function; no other backend.
- FR-I6 (P0) README: hero screenshot, three example prompts per language, install commands, link to examples, coverage badge, star CTA.

### 5.9 Multilingual
- FR-L1 (P0) Four locale packs of equal completeness, CI-enforced.
- FR-L2 (P0) Locked safety terminology per language (closure, danger levels, fire ban, T-grade descriptions), never paraphrased by the model.
- FR-L3 (P0) Source text kept verbatim (original language) beside translated summary and link.
- FR-L4 (P0) Playful strings authored natively per language, not machine-translated.

### 5.10 Data & execution
- FR-D1 (P0) All execution local; user's LLM key or host agent; user's Telegram token; no telemetry.
- FR-D2 (P0) Adapter contract: `fetch`, `freshness`, `licence`, `health`; fixtures and contract tests per adapter.
- FR-D3 (P0) Local cache of static layers (hiking network, protected areas, shooting zones, guardian-dog areas) with TTL; live layers (weather, closures, transport, fire, status) fetched per audit.
- FR-D4 (P0) Web verification performed by the LLM's web tool; each verified status stored with URL, quoted span (≤ 15 words), timestamp, and `verified|unverified|conflicting`.
- FR-D5 (P0) Graceful degradation: any failed adapter yields "could not verify X" in the message and report, never silence.

## 6. Non-functional requirements
- NFR-1 First reply for `find`/`around` ≤ 90 s, `audit` ≤ 120 s on a typical laptop and home connection, excluding LLM latency spikes; progress messages every ≤ 20 s in chat ("checking closures… checking wind…").
- NFR-2 Report renders correctly in iOS Files preview, iOS WhatsApp/Telegram preview, Android Chrome, desktop Chrome/Safari/Firefox; snapshot-tested.
- NFR-3 Works offline for cached static layers with a clear "live data unavailable" banner.
- NFR-4 Python 3.11+, macOS/Linux/WSL; Windows native P2.
- NFR-5 Test coverage: every adapter, every workflow, every locale, register rules, forbidden vocabulary, report snapshots.
- NFR-6 Accessibility: report readable at 200% zoom, colour never the only carrier of severity (icon + label).

## 7. Safety requirements
- SR-1 Evidence classes on every finding: A official fact · B derived fact · C forecast · D interpretation · E judgment required; visible in report, present in `audit.json`.
- SR-2 Safety findings are never removed by constraints, ranking or personalization.
- SR-3 Unverified is displayed as unverified; never inferred open/closed from absence of information.
- SR-4 Avalanche: presence and level only in Phase 1, with explicit "not interpreted for hiking" line.
- SR-5 No route generation off official/known networks.
- SR-6 Emergency short-circuit (FR-C7).
- SR-7 Every report and every audit message ends the warnings block with the fixed localised line: "Bergbot informs. The decision is yours."

## 8. Data sources (Phase 1)
GeoAdmin/swisstopo (search, elevation, hiking network, tiles) · SwitzerlandMobility / cantonal closure feeds (licence check) · MeteoSwiss Open Data (forecast, wind, warnings, webcams) · BAFU/cantonal protected areas, quiet zones, fire danger & restrictions · livestock guardian dogs · Swiss Armed Forces shooting zones & calendar · Open Data Platform Mobility Switzerland (GTFS, cableways) · SLF bulletin (presence/level) · OSM (huts, restaurants, water, shelters, prominence) · live web via LLM tool. A licence/redistribution matrix is a Phase 1 deliverable; where redistribution is not permitted, data is fetched at runtime and never bundled.

## 9. Metrics
Stars · installs by surface (plugin, PyPI, Telegram connects) · audits/finds/exports run (local opt-in counter shown to the user only, no upload) · waitlist signups by source (footer vs website) · language and region mix · benchmark pass rate · safety-regression count (must be 0) · i18n completeness (must be 100%).

## 10. Definition of done (Phase 1)
A first-time user, in any of the four languages, can: connect Telegram or install the plugin from a visual guide in under five minutes · see suggested prompts · ask by constraints, by place, or with a GPX · receive a ≤12-line warnings-first reply and a self-contained mobile report · ask follow-ups and get real answers · request photos/stories for a famous route · receive GPX in the chat and import into swisstopo · forward message and report to someone who can act on them · see and use ★ Star / Install / Waitlist in the footer · inspect sources and code. Bergbot is playful when it can be, serious when it must be, and never says a route is safe. All CI gates green: contracts, safety, register, i18n, snapshots.
